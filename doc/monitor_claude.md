## StormPiX にとって何が解けたか

先の返信で「実機校正をお願いしたい」と書きましたが、**既に済んでいます**。それ以上の収穫がありました。

**1. 斜め圧縮が安全になった** — `drawTriangleF` の塗り規則が厳密に定義されています。これを正しく実装すれば、SSIM 1.0 が実機での一致を意味します。

**2. 円は16角形＝安価な多角形プリミティブ** — 「円」として使うのではなく、16頂点の凸多角形を1命令（引数3個）で塗れる道具として見るべきです。丸みのある塊には矩形階段より圧倒的に安い。

**3. ROM抽出フォントが最大の発見** — `rom/graphics/fonts/tiny.xml` から抽出した実測グリフテーブル（4x5px、送り5px、行送り6px、ASCII 95字）が入っています。これが意味するのは、**`drawText` を可逆な圧縮プリミティブとして使える**ということです。

画像中の4x5領域がどのグリフのピクセルパターンと一致するかを厳密に判定できるので、一致する領域は文字1個で置ける。**データ1文字あたり20ピクセル**です。`drawRectF` の最良ケース（1命令14文字）と比べて桁が違います。HUD・ピクセルアート素材では決定的な差になり得ます。グリフテーブルが実測値なので、近似ではなく可逆です。

前回「将来の拡張候補として最有力」と書いたフォント活用が、推測ではなく厳密に実装できる状態になりました。

**4. 加算合成で色を合成できる** — `setColor` はアルファを取り、モニターは加算発光で合成されます。つまり**半透明を重ねて、setColor の回数より多い色数を作れます**。パレットが色数で制約される前提が崩れます。探索は複雑になりますが、既存2ツールが触っていない次元です。注：カメラ映像が背景の時、この主張は成り立たない。

**5. 忠実性の検証ループが閉じる** — Lua 5.3 WASM でこのラスタライザを通せるので、**生成したLuaを実際に実行して我々の `render()` とビット一致を検証できます**。SSIM が信用できる数値になります。これは品質保証として非常に強い。

## 提起したいこと2点

**ラスタライザの実装が3つに分かれています** — Storm Code（Rust/正典）、PhySim（JS/誤り含む）、StormPiX（矩形のみ）。実機校正で規則を直したとき、1つだけ古くなる状態です。単一の共有パッケージに寄せるべきで、正典が Rust なので WASM で配るか、Rust から生成した参照テストベクタ（入力→期待ピクセル）を全実装が食う形にするのが現実的です。後者なら言語をまたげます。

**StormPiX は Storm Code のパネルであるべきかもしれません** — Lua実行、モニターシミュレーション、StormMin、ワークスペース、共同編集が既にある環境です。画像→Lua変換はその中の1機能として自然に収まります。独立ツールにする積極的な理由（配布の軽さ、単機能の分かりやすさ）もあるので、どちらが良いかは判断をお願いします。当面は独立で進めても、コアを純粋関数ライブラリに保ってあるので後から取り込めます。

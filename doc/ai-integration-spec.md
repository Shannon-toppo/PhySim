# AI連携機能の仕様（ベータ）

2026-11-12に決めた内容です。第1段階（MCPサーバー）と第2段階（パネルへの表示）は、どちらも同じ日に実装しました。

使い方は`doc/next/README.md`の「AIエージェント連携（ベータ）」に、コードの構成は`CLAUDE.md`の「AI tools」に書いています。この文書には、決めたことと、その理由を残します。

## この機能でできること

AIエージェントがPhySimを操作して、マイコンのLuaを自分で確かめながら直せるようにします。エージェントは機体の姿勢を動かし、スクリプトを決まったtick数だけ進め、出力チャンネルやモニターの結果を受け取ります。

Luaの修正はエージェント自身が行います。PhySimが用意するのは操作と観察のための道具で、PhySimがLuaのファイルを書き換えることはありません。

## 対象と公開

対象は2.x系だけです。1.x系には載せません。1.xではLuaを動かしているのがLifeBoatAPIのシミュレーターなので、tick単位の実行もLuaエラーの受け取りもPhySimからはできないためです。

2.xのプレリリースに、ベータ機能として同梱します。2.xを正式版に昇格するときに、ベータの表示を残すか外すかを決めます。

## 提供の形

2段階で作ります。

第1段階は、画面を持たないMCPサーバーです。VSCodeとは別のプロセスで動き、MCPに対応したエージェントならどれからでも使えます。エージェントの実行はVSCodeのパネルには映りません。VSCodeの外で動くので、利用者のPCにNode 22.18以上が必要です。READMEに明記します。

第2段階では、同じ機能を拡張の中から公開し、開いているパネルのギズモとモニターに映します。利用者はエージェントの操作を見ていられます。

## 時間の進め方

時間はtick単位でだけ進めます。エージェントは「姿勢を設定してN tick進め、結果を受け取る」を繰り返します。実時間で流すモードは持ちません。

エージェントの1回の操作には数秒かかるので、60 Hzの実時間で動かしても観察が追いつきません。tick単位にすると、同じ操作が毎回同じ結果になり、修正の前後を比べられます。

## 機体の動きの与え方

次の3通りを用意します。

1. 姿勢を直接指定します。エージェントが位置と回転をそのまま設定します。
2. 位置と速度を設定して、N tick進めます。位置はパネルのSimulateと同じ計算で動きます。この計算は今Webview側の`media/simulation.js`にあるので、Nodeからも使える共有モジュールへ移します。
3. シナリオを読み込んで再生します。形式はパネルのCSVログと同じ列（CH1〜12）にします。パネルで記録した動きを、そのままエージェントの試験に使えます。

## エージェントが操作できるもの

| 操作 | 内容 |
|---|---|
| 実行 | スクリプトの実行開始と停止 |
| 姿勢 | 位置、回転、速度、角速度の設定 |
| 時間 | 指定したtick数だけ進める |
| タッチ | モニターの番号と座標を指定して押す、離す |
| 入力 | 入力チャンネル（数値とbool、1〜32）とプロパティの設定 |
| モニター構成 | 枚数、サイズ、向きの変更 |
| ビルド | `require`の結合、シミュレーター専用部分の除去、minify |

エージェントが設定した入力チャンネルは、スクリプトが`simulator:setInputNumber`などで同じ番号に書けば上書きされます。モニター構成と同じく、スクリプト側の指定が優先です。

MCPサーバー1つにつき、同時に動かせるスクリプトは1本です。

## エージェントが観察できるもの

主な観察手段は数値と文字です。

- 出力チャンネルの値（数値とbool）
- `print`と`debug.log`のログ
- ファイル名と行番号のついたLuaエラー
- ビルド後の文字数と、8192文字の上限までの余裕

モニターは、画素を数値に変換して渡します。エージェントは小さなモニター画像の読み取りを間違えやすいためです。エンジンのフレームは同じ入力なら同じ画素になるので、数値にすれば読み違いが起きません。

3x3のモニターでも9216画素あるので、全画素をそのまま渡すことはしません。次の4種類の問い合わせを用意します。

| 問い合わせ | 返すもの | 確かめられること |
|---|---|---|
| 領域の集計 | 矩形の中の点灯画素数、外接矩形、使われている色 | 配置のずれ、はみ出し |
| 差分 | 前のフレームや修正前のフレームと比べて、変わった画素の数と範囲 | 修正が意図した場所だけを変えたか |
| 期待値との照合 | エージェントが出した条件（この矩形は全部この色、ここは空、など）の合否と、外れた画素の座標 | 描画の仕様どおりか |
| 文字格子 | 32x32程度までの領域を、点灯を`#`、消灯を`.`で表した格子 | 文字の重なり、形の崩れ |

期待値との照合は、`test/ingame.test.mjs`がゲームのスクリーンショットとエンジンの描画を比べているのと同じ考え方です。

整数倍に拡大したPNGも返せるようにします。これは人が見るための補助です。数値で分かるのは「どこに何色があるか」までで、読みやすさや見た目の良し悪しは判定できません。

## 安全性

エージェントが書き換えたLuaを、PhySimは確認なしで実行します。そのため、Luaからできることを2026-11-12に実測しました。探査用のスクリプトを`Simulation`経由でStorm Lua Engine 0.4.1の上で動かした結果です。

| 試したこと | 結果 |
|---|---|
| `io`、`os`、`package`、`coroutine` | 存在しない |
| `load`、`loadfile`、`dofile`、`string.dump` | 存在しない |
| `getmetatable`、`setmetatable`、`rawget`、`_G`、`collectgarbage` | 存在しない |
| `debug` | `debug.log`だけ |
| `require("../outside")`、`require("/etc/passwd")`、`require("..outside")` | 見つからないエラー |
| `async.httpGet(80, "/example")` | 呼べるが、通信は起きない |
| `while true do end` | 「instruction budget exceeded」で実行終了 |
| 約100 GB分の文字列の確保 | 「not enough memory」で実行終了。プロセスのメモリは約76 MBのまま |

スクリプトからファイル、プロセス、ネットワークには触れられません。

`async.httpGet`は、エンジンが要求をキューに積むだけの関数です。送信はホストの役目で、PhySimのホストにはそのキューを読むコードがありません。AI連携機能でも送信は実装しません。

`require`が読めるのは、探索フォルダの下にある`.lua`と`.luah`だけです。ただし、探索フォルダの中に外を指すシンボリックリンクがあれば、その先は読めます。

無限ループが止まるまでの時間は測っていません。3秒以内に終了したことだけ確認しています。

エージェント自身がファイルを書き換えることは、PhySimでは制御しません。エージェントの権限設定で制御します。

## 第2段階で決めたこと

第2段階の目的は、エージェントの操作を利用者がパネルで見られるようにすることです。

当初は「拡張の中から同じツールを公開する」と書き、入口をVSCodeのLanguage Model Toolsにするか、拡張がMCPサーバーを中継するかを未定にしていました。実装では、どちらとも違う形にしました。MCPサーバーを実行の主体のまま残し、サーバーが表示用の情報をウィンドウへ送ります。ウィンドウからサーバーへは何も送りません。

この形にした理由は3つあります。

1. Language Model Toolsは、VSCodeの中のエージェントからしか使えません。Claude Codeなどの外部のエージェントには届きません。
2. 拡張の側にもツールを実装すると、同じ機能が2か所にでき、挙動がずれます。片方向の中継なら、ツールの実装は1つのままです。
3. ウィンドウからサーバーへの経路がなければ、接続先を見つけた別のプロセスがエージェントの実行に手を出すこともできません。

決めた内容は次のとおりです。

| 項目 | 内容 |
|---|---|
| 送るもの | 実行の状態、スクリプトのパス、tick数、姿勢、モニターの構成、変わったモニターの画像、ボタンとスライダーの状態 |
| 送る時機 | 状態を変えるツールの呼び出しごとに1回。読み取りだけのツールとビルドでは送らない |
| つなぐ相手 | スクリプトのフォルダか、その上のフォルダを開いているウィンドウ。近いフォルダのウィンドウを優先する |
| 利用者の実行との関係 | そのウィンドウで利用者が自分のスクリプトを実行している間は、利用者の実行を映す。止めると、エージェントの実行の表示に戻る |
| パネルを開く時機 | エージェントが`start_script`を呼んだときだけ。`physim.autoOpenOnSimulate`に従う |
| 経路 | ホームフォルダの`.physim`の中のローカルのソケット。フォルダもソケットも持ち主だけが使える。Windowsでは名前付きパイプ |

場所を環境変数から決めない点は、テストで見つかった問題への対応です。最初は一時フォルダ（`TMPDIR`）にソケットを置いていました。ところが、エージェントはMCPサーバーを絞った環境変数で起動するので、サーバーとウィンドウで一時フォルダが食い違い、つながりませんでした。ホームフォルダは環境変数がなくても同じ場所に決まります。

Windowsの名前付きパイプには、他のユーザーを締め出すフォルダがありません。名前をフォルダから計算できる形にすると、同じPCの別のユーザーが先にその名前で待ち受けて、画像を受け取れてしまいます。そのため、ウィンドウが推測できない名前を作り、利用者のプロファイルの中のファイルに書きます。サーバーはそのファイルから名前を読みます。

## 確かめたこと、まだ確かめていないこと

macOSでは、Claude Codeから操作して、パネルのモニターとギズモが動くことを2026-11-13に確かめました。

Windowsの名前付きパイプは、Windowsの実機では動かしていません。Linuxも未確認です。

## 実装で決めたこと

仕様を決めた時点では未定だった点と、実装中に分かった点です。

ツールは22個です。名前と引数は`src/agent/tools.ts`にあり、一覧は`doc/next/README.md`に載せています。ベータの間は変わることがあります。

MCPのプロトコル処理は自前で書きました（`src/agent/mcp.ts`）。公式SDKを同梱すると依存パッケージが大きく増えるためです。公式SDKは開発用の依存としてだけ入れ、テストが公式クライアントからサーバーを操作して、プロトコルどおりに動くことを確かめます。

`require`が探すフォルダは、VSCodeなしで決めます。スクリプトから上へたどって、`.git`か、`settings.json`などの入った`.vscode`があるフォルダをワークスペースとみなし、そこの`.vscode/settings.json`を読みます。中身を問わず`.vscode`を目印にすると、VSCodeが拡張機能を置く`~/.vscode`のせいで、ホームフォルダ全体がワークスペースになってしまいます。そのため、ホームフォルダとその上はワークスペースにしません。ユーザー設定は読めないので、`start_script`の`libraryPaths`で補います。

エンジンの規則が、エージェントの実行にもそのまま出ます。`onDraw`の中では`input.*`が0を返します。これはエンジンが決めた挙動で、ゲームの実機が同じかどうかは測定されていません（`doc/storm-lua-engine-requests.md`の4番）。`print`や`require`はゲームにないので、`__LB_SIMULATOR_ONLY__`の外に書くとビルドがエラーにします。この2点はサーバーの説明文に入れて、エージェントに伝えています。

モニターの色は、黒い画面の上で見える色（rgb × alpha / 255）で返します。エンジンのフレームが持つ生のRGBAは返しません。

`build_script`の書き込み先は、ワークスペースのフォルダの中に限りました。シンボリックリンクをたどった先で判定します。ビルドの元になったLuaファイルは上書きしません。既定の`_build/release`以外の場所にある既存のファイルは、`overwrite: true`がない限り上書きしません。サーバーがファイルに書き込むのはこのツールだけです。

`motion`を`integrate`にした`step`で姿勢の値が桁あふれした場合は、そのtickを実行せずにエラーを返します。無限大の値をスクリプトに渡さないためです。

## 独立レビューで直した点

実装の後、別のエージェントにコードを読んでもらい、5件の指摘を受けて直しました。

1. `build_script`の書き込み先の判定が文字列の比較だけで、ワークスペース内のシンボリックリンクを通ると外へ書けました。
2. ワークスペースを探す処理が`~/.vscode`を目印とみなし、プロジェクトの外にあるスクリプトではホームフォルダを返していました。
3. `__proto__`というラベルのプロパティが、設定されずに捨てられていました。
4. `integrate`で姿勢が桁あふれすると、無限大の値がスクリプトに渡っていました。
5. `monitor_grid`の色分けが16色までしか文字を割り当てていませんでした。26色までに直しました。

`step`には、1回36000tickまで、処理時間20秒までの上限を設けました。20秒を超えると、進んだtick数を返して戻ります。

# 実機検証カード

Stormworks 本体でモニター描画規則を確認するためのマイクロコントローラー用 Lua。
実装が解釈で割れる点だけを、スクリーンショットから読み取れる形に並べてある。

| ファイル | 文字数 | ページ |
|---|---|---|
| `verifyA_shapes.lua` | 3,253 | A1–A6: 円・線・三角形の形 |
| `verifyB_color.lua` | 4,032 | B1–B7: 色・アルファ・矩形・文字 |
| `verifyC_circle.lua` | 2,145 | C1–C9: drawCircle のアルゴリズム特定 |
| `verifyD_open.lua` | 6,390 | D1–D12: A〜C で決まらなかった点 |
| `verifyE_sizes.lua` | 4,887 | E1–E7: 3x3 以外のモニター、負の半径の辺数 |
| `verifyF_gaps.lua` | 6,503 | F1–F9: 規則を式で埋めているだけの範囲 |

どれもゲーム内エディタの文字数制限（現在 8,192 字）に収まる。コメントごと貼って構わない。
どれも ASCII だけで書いてある（ゲーム側は2バイト文字を扱えない）。`test/ingame.test.mjs` が確かめている。

## 組み方

1. マイクロコントローラーに **モニター(3x3 = 96x96 推奨)** を1枚。
   MC の映像出力 → モニターの映像入力。
2. **モニターのコンポジット出力 → MC のコンポジット入力**（これがタッチ入力）。
   これを繋がないとページ送りができない。
3. スクリプトを貼り、ビークルに載せてワークベンチから出す。

ページ送りは **画面の右半分タップで次 / 左半分タップで前**。左上に `A3` のように
現在ページが出る。タッチを繋げない場合の保険として、number ch32 にダイヤルを
繋ぐとその値のページへ直接飛べる。

レイアウトは 96x96 前提。大きいモニターでも動くが左上に寄って描かれる。

## 撮り方

- モニターに正対して、**1画素ずつ数えられる距離**まで寄る。
- **1ページ1枚**。撮れたページだけでも構わない。
- ファイル名はページ名（`D4.jpg`）。3x3 以外のモニターで撮ったものは `E2_5x3.jpg`
  のように大きさ（ブロック数、横x縦）を付ける。
- 斜めから撮ると画素の境界が潰れて列が数えられなくなる。

## 各ページが分けるもの

緑は目盛と基準（上端・左端に 5px ごと 1px、10px ごと 2px）。白が被検体。
各ページの「予測」は撮影前に立てた仮説。PhySim は現在、実機のスクリーンショットに合わせてある。

> **A/B 各ページの「予測」は撮影前に書いたもので、実機で複数が否定された。**
> 実測の結果は `doc/ingame-findings.md` を見ること。以下は「そのページが何を分けるか」
> の説明として読む。

### A1 / A2 — 円の分割数・開始角・回転方向
`drawCircle(48,52,22)` と、中心を +0.5 した同じ円。

- 予測: **半径によらず16角形**。角度0(右)から始まり、辺長 0.39×22 ≈ 8.6px。
- A2 は A1 に対しておよそ 1px 右下へずれるだけで、形は変わらない。
- もし真円に見えたら、分割数固定という前提そのものが崩れる。
- 頂点の位置（右端が頂点か、平らな辺か）で **開始角**が決まる。撮影前には予測が
  立っていなかった部分なので、ここが一番の収穫になる。

### A3 — 円が消える半径
上段が輪郭 r=1..7、中段が塗り r=1..7、下段が r=2.4/2.5/2.6/2.7/3.0 の輪郭。

- 予測: 16角形の辺長が 1px 未満だと線が1本も引かれない → **輪郭は r≤2.5 が消え、
  r=2.6 から出る**。塗りは r=1 から全部出る。
- 上段に小さい円が全部出るなら、円は線の集合ではない（＝別経路で描かれている）。

### A4 — 端点の小数をどう丸めるか
上が縦線5本（緑の短い縦棒が整数基準）、下が横線5本（右の緑の短い横棒が整数基準）。
小数部は左から `0, .25, .5, .75, -.25`。

- 予測（round、.5 は 0 から遠い側へ）: 基準に対し **同, 同, +1, +1, 同**
- floor なら: **同, 同, 同, 同, -1**
- 5本目（-.25）が決め手。

### A5 — 1px 未満の線
左が水平線で長さ `0, .3, .5, .7, .9, 1, 1.1, 1.5, 2`（緑の点が各行の目印）。
右が斜めで `(dx,dy) = (.8,.8), (.6,.6), (.9,.4), (1.2,0), (.7,.7)`。

- 予測: **長さ²が 1 未満なら何も描かない**。水平は下4行（1, 1.1, 1.5, 2）だけが出て、
  長さ1は 2画素、長さ2は 3画素。
- 斜めは **1本目 (.8,.8) と 4本目 (1.2,0) だけ**が出る。
  軸ごとの判定（|dx|,|dy| のどちらかが1以上）なら1本目が消えて4本目が残る。
  ここで両者が分かれる。

### A6 — 塗り三角形の境界
上が小数頂点の塗り三角形と整数頂点の輪郭三角形、下が同じ直角三角形の
整数版(右)と +0.5 版(左)。

- 予測: スパンは `ceil(左)`〜`floor(右)`＝**中心が内側にある画素だけ**。
  下段は整数版が 21 行（幅 21,20,…,1）、+0.5 版は **1行少ない 20 行**になる。
- 両方 21 行で同じ形なら、境界が甘い（はみ出す）実装。

### B1 — モニターの伝達特性
不透明グレイ 0,17,34,…,255 の16枚と、RGB 各色の同じ刻み。
画素値を読んでカーブを出す。LifeBoatAPI が `(c/255/0.85)^(1/2.4)` を当てている根拠が
実機と合うかがここで決まる。RGB 3色が同じカーブかも見る。

### B2 — アルファの合成
黒地に白 a=0..255、灰地(128)に白 a=0..255、白地に黒 a=0..255 の3段。
3段の関係から、合成がガンマ前か後か、premultiplied かが決まる。

### B3 — 重ね塗りと低アルファ
上段: a=128 の同じ矩形を 1,2,3,4,5 回重ねたもの。
中段: 白地に `(0,0,0,a=0)`, `(255,0,0,a=0)`, `(0,0,0,a=8)`。
下段: 黒地に白 a=1,2,4,8,16,32,64,128。

- 予測: 上段は 128, 192, 224, 240, 248 へ収束（毎回 src-over）。
- a=0 は何も起きない。a=8 がうっすら出れば下限は 1/255 刻み。
- 上段が飽和せず加算的に伸びるなら合成モデルが違う。

### B4 — drawClear はアルファを無視するか
赤い矩形と青い文字を描いた後に `setColor(0,255,0,128)` で `drawClear()`。

- 予測（＝Wiki の記述）: **アルファに関係なく置換**。全面が緑一色になり、
  下の赤と青は完全に消える。緑の明るさを B1 のランプと突き合わせれば、
  置換値が premultiply 後（≈128）か、そのまま（255）かも分かる。
- 下の絵が透けて見えたらブレンドしている。

### B5 — 枠の四隅と退化ケース
半透明(a=128)の枠、幅1・高さ1・幅0・1x1 の枠、整数/+0.5/+0.25 の枠。

- 予測: **四隅は二重ブレンドしない**（角と辺の中央が同じ明るさ）。
- 幅0 は何も描かない。
- 角だけ明るく見えたら、4辺を素直に引いている実装。

### B6 — drawRectF の座標規則
`x` と `x+w` の整数位置に緑点。矩形は `(20,3) (20.5,3) (20.5,3.5) (20.25,3)
(20.75,3) (19.5,3)` と、最下段に `x=-0.5,w=4` / `w=0` / `w=0.4`。

- 予測（floor）: 20 始まりで幅3 が4本、`20.5,w=3.5` だけ幅4、`19.5` は19始まり。
- round なら `20.5` 系が **21 始まり**になる。ここで分かれる。

### B7 — 文字
4x5 グリフ、送り5px、行送り6px という前提の確認。目盛と突き合わせて
送り幅を数える。小数座標のテキスト、左端の見切れ、`drawTextBox` の折返しも入れてある。

### C1–C9 — drawCircle のアルゴリズム

A3 で **r=1..7 は中点円と完全一致**、A1 の **r=22 は中点円でも16角形でも再現できない**
ことが分かっている。このカードはその間を埋める。中心は4象限に固定
（(25,25) (70,25) (25,70) (70,70)）で、r<=22 なら互いに重ならない。

| ページ | 内容 | 見るところ |
|---|---|---|
| C1 | r=8,9,10,11 | ここまで中点円と一致するか |
| C2 | r=12,13,14,15 | **一致が崩れる境目はこのあたりのはず** |
| C3 | r=16,17,18,19 | |
| C4 | r=20,21,22,22 | 右下は C5 の基準（中心が整数の r=22） |
| C5 | r=22、中心を +0.25 / +0.5 / +0.5(y) / +0.75 | 中心の小数部がどう効くか |
| C6 | r=15, 15.25, 15.5, 15.75 | 半径の小数部が形に効くか（A3 では効いていた） |
| C7 | r=32 を1つ | 大半径での規則 |
| C8 | r=44 を1つ（画面いっぱい） | 同上。1行ずつ境界を読める |
| C9 | `drawCircleF` r=12,13,14,15 | 塗りは輪郭と同じ規則か |

半径ごとに1ページ丸ごと使わず4象限に詰めてあるので、9枚で r=8..22 を1刻み、
プラス大半径2つと塗りが取れる。**C2 と C3 が最優先**（境目がここにあるなら、
実装が半径で切り替わっていることになる）。

このカードは下端にも目盛を入れてある（上端・下端・左端の3本）。較正は A より強い。

> 2026-09-21 の撮影では C5 と C6 がこの表どおりの内容ではなかった（C5 に C6 の円、
> C6 に C9 の塗り）。C5 は撮り直しが要る。`doc/ingame-findings.md` の「撮影データの注意」。

### E1–E7 — 3x3 以外のモニターと、負の半径

`doc/monitor-rendering.md` の「分かっていないこと」のうち2つを測る。

**E1–E4 はモニターの大きさに合わせて描く。** 持っている大きさ全部（1x1 = 32x32、
2x1 = 64x32、3x1 = 96x32、2x2 = 64x64、3x2 = 96x64、3x3、5x3 = 160x96、
9x5 = 288x160）で撮る。
ファイル名は `E2_5x3.jpg` のように大きさを付けてほしい。E1 の左上にも `160X96` のように
大きさを出してある。3x3 の規則がそのまま当てはまるなら、どの大きさでも
`media/raster.js` の予測と画素単位で一致するはず。

| ページ | 内容 | 分けるもの |
|---|---|---|
| E1 | 右端・下端ちょうどの線と塗り、右端で切れる文字 | 画面の端で .5 の丸めと切り取りが 3x3 と同じか。x=W の線と y=H−0.5 の線は何も描かれないはず |
| E2 | 30x21 の検証ブロック（.5 の線、0.5/0.3px の線、ひし形の角、drawRectF と drawRect、塗り三角形、塗り円、文字）を画面全体に敷き詰めたもの | 全ブロックが同じ絵か。1つでも違えば、規則が画面上の位置に依存している |
| E3 | 画面の幅いっぱいの緩い斜線 | 座標の写し方に1画素未満のずれがあれば、段の位置がずれる |
| E4 | 円 r=22,20,18,17,13,9,7,3,26,30,34,44 を入るだけ | 辺数 `clamp(floor(r/2), 8, 16)` が画面の大きさに依らないか |

ブロックの間隔は横 32・縦 23 の整数なので、どのブロックも同じ画素になるのが
正しい。1x1 では1個、3x3 では9個、9x5 では54個並ぶ。

**E5–E7 は 3x3（96x96）で撮る。** D12 で r=−10 と −8 は正の半径と同じ形だったが、
どちらも八角形なので、辺数の式に負の値がどう入るかは分からなかった。

| ページ | 内容 |
|---|---|
| E5 | 輪郭 r = −22, −18, −19, −21（4象限） |
| E6 | 同じ半径の塗り |
| E7 | 同心の輪郭 r = −44, −32, −26 |

仮説は、辺数が N = clamp(floor(r/2)) そのもの（負なら常に 8。PhySim の現状）、
clamp(floor(\|r\|/2))、clamp(\|floor(r/2)\|) の3通り。辺数が奇数になる半径では、
頂点を r で置く（角度0の頂点が左を向く）か \|r\| で置く（A1 と同じく右を向く）かも
分かれる。

| r | そのまま | \|r\| | \|floor\| |
|---|---|---|---|
| −22 | 8 | 11 | 11 |
| −18 | 8 | 9 | 9 |
| −19 | 8 | 9 | 10 |
| −21 | 8 | 10 | 11 |
| −44, −32 | 8 | 16 | 16 |
| −26 | 8 | 13 | 13 |

6通り（辺数3通り × 頂点の符号2通り）の組の差は、E5 で最小 172 画素、E6 で最小
99 画素（辺数が8のときは頂点の符号で絵が変わらないので、その組は除く）。E7 は
「そのまま」とそれ以外を 960 画素、頂点の符号を 120 画素で分ける。

> 大きさに依らず、負の半径は |r| の円と同じだった。`doc/ingame-findings.md` の8節。

### F1–F9 — 式で埋めているだけの範囲

`doc/monitor-rendering.md` の規則のうち、撮ったページの外側へ式を延ばして使って
いるところを測る。すべて 3x3（96x96）で撮る。上・下・左の3本の目盛入り。

図形のページ（F1〜F6、F9）は、PhySim の予測と対立する仮説で何画素違う絵になるかを
シミュレータで確かめてある。

| ページ | 内容 | 分けるもの（仮説間の差） |
|---|---|---|
| F1 | 同心の輪郭 r=23, 25, 27, 29, 31, 33 | 辺数 `floor(r/2)` の境目。どの円も辺数が ±1 違えば 78〜112 画素変わる。round(r/2) なら全体で 454 画素 |
| F2 | 同心の輪郭 r=24, 25.9, 28, 29.9, 31.9 | 同上。x.9 は floor と round で辺数が分かれる半径（全体で 314 画素） |
| F3 | 塗り（drawRectF の x、y、drawTriangleF、drawCircleF）の頂点を 0 / 1/1000 / 1/512 / 1/300 ずらした 4x4 の表。下端に半径0の円と、頂点が小数の drawTriangle | 塗りも 1/256 に丸めるか。丸めなしと 1/512 格子は 36 画素、1/128 は 48 画素、ちょうど半分（1/512）を偶数へ丸めるなら 20 画素違う |
| F4 | D1 の r=22 の円を塗ったもの（中心 +0.25 / +0.5 / +0.5(y) / +0.75） | 小数中心の塗り円。標本点が 1/16px ずれるだけで 16〜18 画素違う |
| F5 | 十角形（r=20, 21）の水平な辺を、標本点の行にちょうど乗せた塗り円4つ（上の辺2つ、下の辺2つ） | 塗り円の縁の扱い。上の縁を点け下の縁を点けない規則が逆なら 52 画素 |
| F6 | r=29 の塗り円（十四角形、上の辺が行 20 に乗る）と、画面外 ±1e5〜±1e9 から来る線7本 | 縁の扱い（13 画素）、大きい塗り円、急な傾きと緩い傾きの画面外の線 |
| F7 | 色付きの半透明（下の表） | 合成の式が色ごとに効くか。文字・線・円の半透明 |
| F8 | 半透明の橙 (255,128,0,64) で drawClear したページ（下の表） | drawClear が置き換えるアルファ、その上へのブレンド |

F7 は上に不透明のランプ（灰・R・G・B を 0〜255 の 51 刻み）があり、同じ画像の中で
較正できる。下の3段は地の色が黒・灰(128)・白で、各段に次のものが並ぶ。

| | 黒地 | 灰地 | 白地 |
|---|---|---|---|
| 赤 a=128 | 96,0,0 | 144,48,48 | 191,95,95 |
| 緑 a=128 | 0,96,0 | 48,144,48 | 95,191,95 |
| 青 a=128 | 0,0,96 | 48,48,144 | 95,95,191 |
| 橙 (255,128,0) a=128 | 96,48,0 | 144,96,48 | 191,143,95 |
| シアン a=128 | 0,96,96 | 48,144,144 | 95,191,191 |

各段の2列目は、不透明の色の上に半透明の色を重ねたもの（地の色に依らない）。

白に赤 a=64 → 207,155,155。灰(128)に橙 a=192 → 183,104,26。

## 撮影したスクリーンショットの解析

`analysis/` に解析ツールが入っている。緑の目盛を較正ターゲットにして
スクリーンショットをモニターの論理格子へ戻す。目盛は上・下・左のうちあるものを
全部使う（A は上＋左、B は上＋下、C〜F は3本）。

モニターの大きさはファイル名から読む（`analysis/screen.mjs`）。`E2_5x3.png` は
5x3（160x96）、大きさの付いていない `A1.png` は 3x3（96x96）。1ブロック 32 画素。
同じ名前が fixture のページのキーになり、`test/ingame.test.mjs` もそこから
画面の大きさを決める。

```bash
node tools/ingame/analysis/rectify.mjs <shot.png> <out.ppm>   # 復元 + 較正残差を表示
node tools/ingame/analysis/show.mjs    <shot.png> 150 28 76   # 点灯画素をASCIIで表示
node tools/ingame/analysis/compare.mjs <shot.png> <expected.ppm> # 期待画像との差分
node tools/ingame/analysis/export-fixture.mjs <macPngDir> <winPngDir> test/fixtures/ingame-raster.json
```

`export-fixture.mjs` は図形と文字のページ（A1–A6, B5–B7, C1–C4, C7–C9, D1–D8,
D10–D12 は必須、E と F は見つかったもの全部。F7・F8 は色のページ、F3 は
プラットフォームで食い違うので除く）の点灯画素を `test/ingame.test.mjs` 用の
fixture に書き出す。どこもマスクしない（緑の目盛と文字は輝度 137 以下で、閾値 150
に届かない）。両プラットフォームが1画素でも食い違うか、較正残差の平均が 0.1px を
超えたページがあれば書き出さずに止まる。
`RECTIFY_DEBUG=1` を付けると、残差 0.1px を超えた目盛を個別に表示する。

入力は PNG（`sips -s format png a.jpg --out a.png` で変換）。
較正が効いているかは `residual mean` で判断する。3x3 までは 0.04px 以下に収まる。
9x5 は論理 1px が画面 5px ほどしかなく 0.06px 前後になるが、これで画素は全部合う。
**0.1px 以下なら信用してよい。** 0.3px を超えていたら目盛の検出に失敗しているので、
結果を読んではいけない。

結果は `doc/ingame-findings.md`。

# Storm Lua Engineへの要望

PhySim 2.0をStorm Lua Engine 0.4.1の上に作る中で出てきた要望をまとめます。

最初の版は2026-11-13に、npmパッケージの型定義だけを見て書きました。その後、エンジンのリポジトリを0.4.1（コミット`88ec6f0`）まで更新し、仕様書、`CHANGELOG.md`、`TASKS.md`、ソースと照らして全項目を確かめ直しました。この文書はその結果を反映した版です。各項目に、何で確かめたかを書いています。

PhySimはVSCodeの拡張機能で、Stormworksのマイコン用Luaをエンジン上で実行します。使っているのは、ビークル用のVM（`createVehicle`、`extended`環境）、デバッガ、モニターの描画、コンパイラ（`buildLifeboat`）です。

エンジンに置き換えた結果、PhySimが自前で持っていた通信、描画、ビルドの実装はすべて不要になりました。ゲームのスクリーンショット86ページとの比較でも、エンジンの描画は画素単位で一致しています。以下は、そのうえで「あると助かる」ものです。

## 確かめ直して変わった点

最初の版から、次の3点が変わりました。

- 「版ごとの変更点の一覧がほしい」という要望は取り下げます。`CHANGELOG.md`が0.4.1まで書かれていました。手元のリポジトリが0.2.0の頃のままで、気づいていませんでした。
- 「エラーの種類を区別したい」という要望は、半分がすでに実現していました。`EngineError`の`code`が種類を表しています。残るのは、エラーの位置の情報です。
- `onDraw`の中の`input.*`は、「確認したいこと」から「測定してほしいこと」に変えました。仕様書に、ゲームの実機では測定していないと書かれていたためです。

## 回避できず、機能を諦めているもの

`docs/specs/debugger.md`を読み、3件とも今のエンジンにない機能だと確かめました。この仕様書は、停止の方法としてブレークポイントとステップだけを挙げています。壁時計による打ち切りも未実装と明記されています。

### 1. 外からの一時停止

デバッガの一時停止ボタンが使えません。エンジンが実行を止めるのは、ブレークポイントに当たったときと、ステップ実行のときだけです。外から「次の行で止まれ」と頼む方法がないので、PhySimは一時停止の要求をエラーで返しています。

実行中のVMに対して、次に実行する行で止まるよう頼むAPIがほしいです。たとえば`vm.requestPause()`を呼ぶと、次の行で`suspended`が返る形です。

無限ループに入ったスクリプトを止めて、どの行にいるかを見る用途でも使います。今は命令数の上限でエラーになるのを待つしかなく、エラーになった時点ではVMの中を見られません。

### 2. tickをまたぐステップ実行

`onTick`の最後の行でステップオーバーすると、そのtickが終わり、スクリプトはそのまま走り続けます。次のtickの`onTick`の先頭では止まりません。

`resume("over")`や`resume("into")`で関数の終わりを越えたとき、ステップの状態を次の入口の呼び出しまで持ち越す指定がほしいです。次に`tick()`や`draw()`を呼んだとき、最初の行で止まる動きを想定しています。

### 3. ブレークポイントを置ける行の一覧

PhySimは、利用者が置いたブレークポイントをすべて「有効」として表示しています。その行に実行できるコードがあるかどうかを、エンジンに聞く方法がないためです。空行やコメント行に置いたブレークポイントは、有効と表示されたまま一度も止まりません。

読み込んだチャンクごとに、ブレークポイントを置ける行番号の一覧を取れるとよいです。Luaの`debug.getinfo`が返す`activelines`に当たる情報です。これがあれば、置けない行のブレークポイントを次の有効な行へ移すか、無効と表示できます。

## ゲームとの一致を測定してほしいもの

### 4. `onDraw`の中の`input.*`

`onDraw`の中で`input.getNumber`を呼ぶと、エンジンは0を返します。`output`への書き込みも無視されます。実機のエンジンで動かして確かめました。コンパイラも`input-outside-ontick`という診断で警告します。

`docs/specs/numeric-io.md`には、これが「エンジン契約」であり、「実ゲームの全異常系を測定済みではない」と書かれています。つまり、ゲームの実機が同じ値を返すかどうかは、まだ分かっていません。

ゲームの実機の挙動として、考えられるのは3通りです。

1. 値を返す。この場合、`onDraw`の中で入力を読む既存のスクリプトは、PhySimでだけ表示が0になります。利用者には、スクリプトの誤りに見えます。
2. 0を返す。この場合、今のエンジンで正しいです。
3. エラーになってスクリプトが止まる。PhySimの作者には、実機でそうなった覚えがあります。確かめたものではなく、記憶です。この場合、ゲームで動かないスクリプトが、PhySimでは何も言わずに動いてしまいます。誤りを見つける道具としては、いちばん困る食い違いです。

コンパイラの警告が「`input.*`は`onTick`の中でしか参照できない」という文面であることは、3とも合います。

ゲームの実機で測定し、結果に合わせてほしいです。3だった場合は、エンジンもエラーにするのが望ましいです。少なくとも`extended`環境では、警告をログに出す選択肢があると助かります。どの結果でも、測定したことが仕様書に書いてあれば、利用側が説明できます。

PhySimの側でも実機で試せます。結果が出たら共有します。

### 5. `map.screenToMap`と`map.mapToScreen`

ビークル用の環境に`map`テーブルがありません。実機のエンジンで`type(map)`を調べると`nil`でした。ゲームにはあるので、これを呼ぶスクリプトは`attempt to index a nil value (global 'map')`で止まります。

`TASKS.md`には「map座標変換」が、「実利用要求がある段階で入力・精度を検証して追加」する項目として載っています。この要望が、その実利用要求に当たります。

PhySimは、スクリプトより先に読み込むLuaで`map.screenToMap`と`map.mapToScreen`を定義しています。式はLifeBoatAPIのシミュレーターのものを使いました。ゲームの実際の計算と一致するかは確かめていません。

もう1点、食い違いがあります。`crates/storm-lua-spec/src/environment.rs`の`VEHICLE_ROOTS`には`map`が入っています。コンパイラは`map`を既知の名前として受け付けるのに、VMで実行すると`nil`です。ビルドは通り、実行で止まることになります。

## PhySim側で回避しているもの

### 6. エラーの位置を構造で受け取りたい

エラーの種類は、`EngineError`の`code`で分かります。実機のエンジンで確かめたところ、Luaのエラーは1、命令数やメモリの上限は2でした。`crates/storm-lua-bridge/src/lib.rs`の`Status`と同じ番号です。PhySimは今、種類を区別せず、メッセージをそのまま利用者とAIエージェントに見せています。「スクリプトの誤り」と「上限に達した」ではエージェントの次の行動が変わるので、`code`から種類を付けて返すよう、PhySim側を直す予定です。

`code`の番号と意味の対応は、TypeScriptの側に定数として見当たりませんでした。`Status`に当たる定数が公開されていると、数値を直接書かずに済みます。

残る要望は位置の情報です。`EngineError`が持つのは`code`と`message`だけで、PhySimはエラーの起きたファイルと行を、メッセージの文字列から読み取っています。

困るのは、Luaがメッセージの中のチャンク名を切り詰める点です。長いパスのチャンク名でエラーを起こすと、メッセージは`...t/goes/on/and/on/for/more/than/sixty/characters/main.lua:1: x`のように先頭が省略されました。同じ名前のファイルが複数あると、どのファイルか確定できません。

エラーに次の情報を持たせてほしいです。

- 省略されていないチャンク名と行番号
- 呼び出し履歴（`stack()`と同じ形の配列）
- 構文エラーと実行時エラーの区別。どちらも`code`は1で、今は`syntax error`と`runtime error`という文字列でしか見分けられません

ログには、0.2.1でチャンク名と行番号（`LogRecord.location`）が付きました。エラーにも同じ形で付くと、扱いが揃います。

### 7. コンパイラのWASMをパッケージの`exports`に入れてほしい

0.4.1の`packages/lua-engine/package.json`で確かめました。`exports`には`./wasm/*`があり、実行用のWASMは`require.resolve`で場所が分かります。コンパイラのWASM（`dist/compiler-wasm/compiler_bg.wasm`）は`exports`にありません。

VSCodeの拡張機能では、WASMをディスクから読んで`wasmBinary`として渡す必要があります。拡張機能のホストが`file:`のURLを`fetch`できるとは限らないためです。PhySimは、実行用WASMの場所から相対パスでコンパイラのWASMを探しています。パッケージの中の配置が変わると壊れます。

`./compiler-wasm/*`を`exports`に足してほしいです。

### 8. プロパティを1つだけ設定したい

`packages/lua-engine/src/runtime.ts`にあるのは、`properties()`と`setProperties()`だけでした。

実行中にプロパティを1つ変えるとき、PhySimは`vm.properties()`で全体を読み、該当する1件を差し替えて、`vm.setProperties()`で全体を書き戻しています。ラベルがバイト列のこともあるので、比較のために文字列へ直す処理も入ります。

`vm.setProperty(label, value)`があると簡単になります。

### 9. フレームが変わったかどうか

`packages/lua-engine/src/frame.ts`に、フレームの世代や変更の有無を表す値は見当たりませんでした。

PhySimは、モニターの画像が前のtickと同じなら送りません。そのために、毎tick`frame().copy()`で画素を写し取り、前回の画素とバイト単位で比べています。

描画の結果が前回と同じかどうかをエンジンが教えてくれれば、写し取りと比較を省けます。フレームごとの通し番号やハッシュ値でも足ります。

## 文書にほしいこと

### 10. 必要なNodeのバージョン

パッケージは`node >= 22.18`を求めています。`docs/design/distribution.md`には、ビルドに使う道具として「Nodeは22.18以降」と書かれていました。実行時に22.18が必要な理由は見つかりませんでした。

VSCodeの拡張機能は、VSCodeに組み込まれたNodeで動くので、この条件がそのまま「対応するVSCodeのバージョン」を決めます。PhySimは`^1.101.0`としていますが、どのVSCodeから条件を満たすかは確かめられていません。

22.18が要るのがビルドのときだけなら、`engines`を実行に必要な版まで緩めてもらえると、対応できるVSCodeが広がります。

### 11. CommonJSからの読み込み

パッケージはESMだけです。案内の文書に、CommonJSから使う方法は見当たりませんでした。

VSCodeの拡張機能はCommonJSで書くのが今も一般的なので、PhySimは動的な`import()`で読み込み、型の読み込みにも専用の書き方をしています。動いてはいますが、TypeScriptの設定を`Node16`に変える必要がありました。

対応は急ぎません。案内の文書に「CommonJSから使う方法」の例があると、他の拡張機能の作者が助かります。

### 12. ホストのコールバックに届くLuaの文字列

ホスト側の関数に届くLuaの文字列は`Uint8Array`です。`docs/specs/debugger.md`には「文字列はbytes」「JS APIはUint8Arrayを用いる」と書かれていて、設計としては明記されています。

利用者向けの案内（`docs/guide`）のほうには、ホストのコールバックについてこの説明が見当たりませんでした。PhySimでは最初、文字列が`49,120,49`のような数字の並びに化けて、原因が分かりませんでした。

案内の`bindings`の例に、ひとこと書いてあると迷いません。

## 優先度

PhySimにとって効果が大きい順に並べると、次のようになります。

| 順位 | 要望 | 理由 |
|---|---|---|
| 1 | 4. `onDraw`の中の`input.*`の測定 | ゲームと違っていた場合、表示が黙って0になるか、ゲームで動かないスクリプトがPhySimでは動いてしまう |
| 2 | 6. エラーの位置 | すべての利用者とAIエージェントが毎回目にする。今は文字列の解析に頼っている |
| 3 | 1. 外からの一時停止 | デバッガとして期待される機能が欠けている |
| 4 | 3. ブレークポイントを置ける行 | 止まらないブレークポイントは、原因に気づきにくい |
| 5 | 2. tickをまたぐステップ | 1つのtickの中しか追えない |
| 6 | 5. `map`の関数 | 使うスクリプトは多くないが、今は検証していない式で代用している |
| 7 | 7. コンパイラのWASMの`exports` | 小さな変更で、壊れやすい箇所が1つ消える |

8と9は、あれば実装が簡単になる程度です。10〜12は文書の話で、エンジンの機能は変わりません。

# 実機検証カード

Stormworks 本体でモニター描画規則を確認するためのマイクロコントローラー用 Lua。
実装が解釈で割れる点だけを、スクリーンショットから読み取れる形に並べてある。

| ファイル | 文字数 | ページ |
|---|---|---|
| `verifyA_shapes.lua` | 3,262 | A1–A6: 円・線・三角形の形 |
| `verifyB_color.lua` | 4,019 | B1–B7: 色・アルファ・矩形・文字 |
| `verifyC_circle.lua` | 2,167 | C1–C9: drawCircle のアルゴリズム特定 |

どちらもゲーム内エディタの 4,096 文字制限に収まる。コメントごと貼って構わない。

## 組み方

1. マイクロコントローラーに **モニター(3x3 = 96x96 推奨)** を1枚。
   MC の映像出力 → モニターの映像入力。
2. **モニターのコンポジット出力 → MC のコンポジット入力**（これがタッチ入力）。
   これを繋がないとページ送りができない。
3. スクリプトを貼り、ビークルに載せてワークベンチから出す。

ページ送りは **画面の右半分タップで次 / 左半分タップで前**。左上に `A3` のように
現在ページが出る。タッチを繋げない場合の保険として、number ch32 にダイヤルを
繋ぐとその値のページへ直接飛べる。

レイアウトは 96x96 前提。大きいモニターでも動くが左上に寄って描かれる。

## 撮り方

- モニターに正対して、**1画素ずつ数えられる距離**まで寄る。
- **1ページ1枚**。全13枚。撮れたページだけでも構わない。
- 斜めから撮ると画素の境界が潰れて列が数えられなくなる。

## 各ページが分けるもの

緑は目盛と基準（上端・左端に 5px ごと 1px、10px ごと 2px）。白が被検体。
「正典」は Storm Code `screen_raster.rs` の挙動。撮影の結果、線・円・塗りの規則は
正典が間違っていた。PhySim は現在、実機のスクリーンショットに合わせてある。

> **A/B 各ページの「正典の予測」は撮影前に書いたもので、実機で複数が否定された。**
> 実測の結果は `doc/ingame-findings.md` を見ること。以下は「そのページが何を分けるか」
> の説明として読む。

### A1 / A2 — 円の分割数・開始角・回転方向
`drawCircle(48,52,22)` と、中心を +0.5 した同じ円。

- 正典: **半径によらず16角形**。角度0(右)から始まり、辺長 0.39×22 ≈ 8.6px。
- A2 は A1 に対しておよそ 1px 右下へずれるだけで、形は変わらない。
- もし真円に見えたら、分割数固定という前提そのものが崩れる。
- 頂点の位置（右端が頂点か、平らな辺か）で **開始角**が決まる。正典は「未確認」と
  明記している部分なので、ここが一番の収穫になる。

### A3 — 円が消える半径
上段が輪郭 r=1..7、中段が塗り r=1..7、下段が r=2.4/2.5/2.6/2.7/3.0 の輪郭。

- 正典: 16角形の辺長が 1px 未満だと線が1本も引かれない → **輪郭は r≤2.5 が消え、
  r=2.6 から出る**。塗りは r=1 から全部出る。
- 上段に小さい円が全部出るなら、円は線の集合ではない（＝別経路で描かれている）。

### A4 — 端点の小数をどう丸めるか
上が縦線5本（緑の短い縦棒が整数基準）、下が横線5本（右の緑の短い横棒が整数基準）。
小数部は左から `0, .25, .5, .75, -.25`。

- 正典（round、.5 は 0 から遠い側へ）: 基準に対し **同, 同, +1, +1, 同**
- floor なら: **同, 同, 同, 同, -1**
- 5本目（-.25）が決め手。

### A5 — 1px 未満の線
左が水平線で長さ `0, .3, .5, .7, .9, 1, 1.1, 1.5, 2`（緑の点が各行の目印）。
右が斜めで `(dx,dy) = (.8,.8), (.6,.6), (.9,.4), (1.2,0), (.7,.7)`。

- 正典: **長さ²が 1 未満なら何も描かない**。水平は下4行（1, 1.1, 1.5, 2）だけが出て、
  長さ1は 2画素、長さ2は 3画素。
- 斜めは **1本目 (.8,.8) と 4本目 (1.2,0) だけ**が出る。
  軸ごとの判定（|dx|,|dy| のどちらかが1以上）なら1本目が消えて4本目が残る。
  ここで両者が分かれる。

### A6 — 塗り三角形の境界
上が小数頂点の塗り三角形と整数頂点の輪郭三角形、下が同じ直角三角形の
整数版(右)と +0.5 版(左)。

- 正典: スパンは `ceil(左)`〜`floor(右)`＝**中心が内側にある画素だけ**。
  下段は整数版が 21 行（幅 21,20,…,1）、+0.5 版は **1行少ない 20 行**になる。
- 両方 21 行で同じ形なら、境界が甘い（はみ出す）実装。

### B1 — モニターの伝達特性
不透明グレイ 0,17,34,…,255 の16枚と、RGB 各色の同じ刻み。
画素値を読んでカーブを出す。LifeBoatAPI が `(c/255/0.85)^(1/2.4)` を当てている根拠が
実機と合うかがここで決まる。RGB 3色が同じカーブかも見る。

### B2 — アルファの合成
黒地に白 a=0..255、灰地(128)に白 a=0..255、白地に黒 a=0..255 の3段。
3段の関係から、合成がガンマ前か後か、premultiplied かが決まる。

### B3 — 重ね塗りと低アルファ
上段: a=128 の同じ矩形を 1,2,3,4,5 回重ねたもの。
中段: 白地に `(0,0,0,a=0)`, `(255,0,0,a=0)`, `(0,0,0,a=8)`。
下段: 黒地に白 a=1,2,4,8,16,32,64,128。

- 正典: 上段は 128, 192, 224, 240, 248 へ収束（毎回 src-over）。
- a=0 は何も起きない。a=8 がうっすら出れば下限は 1/255 刻み。
- 上段が飽和せず加算的に伸びるなら合成モデルが違う。

### B4 — drawClear はアルファを無視するか
赤い矩形と青い文字を描いた後に `setColor(0,255,0,128)` で `drawClear()`。

- 正典（＝Wiki の記述）: **アルファに関係なく置換**。全面が緑一色になり、
  下の赤と青は完全に消える。緑の明るさを B1 のランプと突き合わせれば、
  置換値が premultiply 後（≈128）か、そのまま（255）かも分かる。
- 下の絵が透けて見えたらブレンドしている。

### B5 — 枠の四隅と退化ケース
半透明(a=128)の枠、幅1・高さ1・幅0・1x1 の枠、整数/+0.5/+0.25 の枠。

- 正典: **四隅は二重ブレンドしない**（角と辺の中央が同じ明るさ）。
- 幅0 は何も描かない。
- 角だけ明るく見えたら、4辺を素直に引いている実装。

### B6 — drawRectF の座標規則
`x` と `x+w` の整数位置に緑点。矩形は `(20,3) (20.5,3) (20.5,3.5) (20.25,3)
(20.75,3) (19.5,3)` と、最下段に `x=-0.5,w=4` / `w=0` / `w=0.4`。

- 正典（floor）: 20 始まりで幅3 が4本、`20.5,w=3.5` だけ幅4、`19.5` は19始まり。
- round なら `20.5` 系が **21 始まり**になる。ここで分かれる。

### B7 — 文字
4x5 グリフ、送り5px、行送り6px という前提の確認。目盛と突き合わせて
送り幅を数える。小数座標のテキスト、左端の見切れ、`drawTextBox` の折返しも入れてある。

### C1–C9 — drawCircle のアルゴリズム

A3 で **r=1..7 は中点円と完全一致**、A1 の **r=22 は中点円でも16角形でも再現できない**
ことが分かっている。このカードはその間を埋める。中心は4象限に固定
（(25,25) (70,25) (25,70) (70,70)）で、r<=22 なら互いに重ならない。

| ページ | 内容 | 見るところ |
|---|---|---|
| C1 | r=8,9,10,11 | ここまで中点円と一致するか |
| C2 | r=12,13,14,15 | **一致が崩れる境目はこのあたりのはず** |
| C3 | r=16,17,18,19 | |
| C4 | r=20,21,22,22 | 右下は C5 の基準（中心が整数の r=22） |
| C5 | r=22、中心を +0.25 / +0.5 / +0.5(y) / +0.75 | 中心の小数部がどう効くか |
| C6 | r=15, 15.25, 15.5, 15.75 | 半径の小数部が形に効くか（A3 では効いていた） |
| C7 | r=32 を1つ | 大半径での規則 |
| C8 | r=44 を1つ（画面いっぱい） | 同上。1行ずつ境界を読める |
| C9 | `drawCircleF` r=12,13,14,15 | 塗りは輪郭と同じ規則か |

半径ごとに1ページ丸ごと使わず4象限に詰めてあるので、9枚で r=8..22 を1刻み、
プラス大半径2つと塗りが取れる。**C2 と C3 が最優先**（境目がここにあるなら、
実装が半径で切り替わっていることになる）。

このカードは下端にも目盛を入れてある（上端・下端・左端の3本）。較正は A より強い。

> 2026-09-21 の撮影では C5 と C6 がこの表どおりの内容ではなかった（C5 に C6 の円、
> C6 に C9 の塗り）。C5 は撮り直しが要る。`doc/ingame-findings.md` の「撮影データの注意」。

## 期待画像の作り方

正典で同じページを描いた画像は、Storm Code のクレートをそのまま使って出せる。

```bash
cargo run --release --manifest-path <scratch>/pagerender/Cargo.toml -- \
  tools/ingame/verifyA_shapes.lua 6 <出力先>/A
```

`lua-runtime-core` を（`lua` フィーチャ有効で）依存に取り、`LuaUnit::new` →
右半分タップを `CompositeSignal` で n-1 回送ってページを進め → `on_draw` に
`ScreenRaster` を渡して `rgba` を PPM に落とすだけ。

## 撮影したスクリーンショットの解析

`analysis/` に解析ツールが入っている。緑の目盛を較正ターゲットにして
スクリーンショットを 96x96 の論理格子へ戻す。目盛は上・下・左のうちあるものを
全部使う（A は上＋左、B は上＋下、C は3本）。

```bash
node tools/ingame/analysis/rectify.mjs <shot.png> <out.ppm>   # 復元 + 較正残差を表示
node tools/ingame/analysis/show.mjs    <shot.png> 150 28 76   # 点灯画素をASCIIで表示
node tools/ingame/analysis/compare.mjs <shot.png> <canon.ppm> # 期待画像との差分
node tools/ingame/analysis/export-fixture.mjs <macPngDir> <winPngDir> test/fixtures/ingame-raster.json
```

`export-fixture.mjs` は図形だけのページ（A1–A6, B5, B6, C1–C4, C7–C9）の点灯画素を
`test/raster.test.mjs` 用の fixture に書き出す。両プラットフォームが1画素でも
食い違うか、残差が 0.05px を超えたページがあれば書き出さずに止まる。
`RECTIFY_DEBUG=1` を付けると、残差 0.1px を超えた目盛を個別に表示する。

入力は PNG（`sips -s format png a.jpg --out a.png` で変換）。
較正が効いているかは `residual mean` で判断する。**0.05px 以下なら信用してよい。**
0.3px を超えていたら目盛の検出に失敗しているので、結果を読んではいけない。

`pagerender.rs` / `pagerender.Cargo.toml` は Storm Code の Lua VM で同じ
スクリプトを走らせて期待画像を出すためのもの。`storm-lua-runner` が隣に
クローンされている前提。

結果は `doc/ingame-findings.md`。

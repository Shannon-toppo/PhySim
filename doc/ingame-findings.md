# 実機検証の結果（Stormworks v1.15.23 / Apple M5・RTX 4070Ti）

`tools/ingame/verifyA_shapes.lua` / `verifyB_color.lua` / `verifyC_circle.lua` /
`verifyD_open.lua` をゲーム内で実行し、`tools/ingame/image/{appleM5,RTX4070Ti}/` の
スクリーンショットを解析した結果。2026-09-21 時点。D カードは Windows で撮影し、
D9 だけ Mac でも撮った。

**結論：モニターの描画は GPU のラスタライズ規則そのもので、図形は Mac と Windows で
1画素も違わない。** A・B・C の全ページで両者の点灯画素集合が完全一致した。
（例外は頂点がちょうど 1/512px のタイに乗ったときで、F3 で 17 画素違った。9節・10節）
`media/raster.js` / `media/pixelFont.js` はこの規則で書き直してあり、撮影した
27 ページ全部を画素単位で再現する（`test/ingame.test.mjs` がカードのスクリプトを
そのまま実行し、スクリーンショット由来の fixture と突き合わせる）。

## 解析の方法と精度

スクリーンショットを緑の目盛で 96x96 の論理格子へ射影変換で戻す
（`tools/ingame/analysis/rectify.mjs`）。今回、較正を書き直した。

- 旧版は上端＋左端の目盛が前提で、**左目盛の無い B カードは較正できなかった**。
  Windows (8.6 screen px / 論理px) では 1x1 の目盛が 55 画素しかなく、`n >= 60` の
  足切りにも落ちていた。
- 新版は目盛の列を直線として探し（RANSAC）、上・下・左のどれがあっても使う。
- 隅で2本の目盛が融合した塊（左 y=95 と下 x=0 など）は重心がどちらにも属さない。
  C カードで worst 0.5px の外れ値になっていたのがこれで、隅の目盛は除外する。

| カード | 目盛 | residual mean | worst |
|---|---|---|---|
| A1–A6 | 上＋左 | 0.011–0.026px | 0.066px |
| B1–B3, B5–B7 | 上＋下 | 0.012–0.028px | 0.091px |
| C1–C9 | 上＋下＋左 | 0.012–0.035px | 0.103px |

全ページが 0.05px 以下。B4 は全面が単色で目盛が無いので較正しない（不要）。
点灯判定は輝度 150。点灯 236 / 消灯 65 以下にきれいに分かれる。

## 1. drawLine — diamond-exit 規則

画素 (px, py) は、スクリプト座標で (px, py) を中心とするひし形
`|x−px| + |y−py| < 1/2` を持つ（ゲームの半画素オフセットで画素中心が整数に来る）。
**線分がそのひし形に触れ、かつひし形の中で終わらないとき、その画素が点灯する。**
D3D / GL / Metal の非アンチエイリアス線の規則そのもの。

- 終点の画素は点灯しない。区間は `[始点, 終点)`。
- 長さ 0.5 の線は1画素点灯し（ひし形の角で終わる）、0.3 は描かれない。
  「1px 未満は描かない」という閾値は存在しない。
- **端点は 1/256px に丸められる**（GPU の 8bit サブピクセル精度）。D6 で、タイから
  1/1024 ずらした線がタイそのものとして描かれた。丸めなしだと 44 画素、1/512 だと
  30 画素ずれる。1/128 では D1 が崩れる。

### ひし形の縁の扱い（D4・D7 で確定）

ひし形は**半開集合**で、縁ちょうどの点を含むかどうかは次のとおり。

| | 辺（角以外） | 上の角 | 右の角 | 下の角 | 左の角 |
|---|---|---|---|---|---|
| x 主軸の線（45° を含む） | 含まない | **含む** | 含まない | 含まない | 含まない |
| y 主軸の線 | 含まない | **含む** | **含む** | 含まない | 含まない |

この1つの表で次が全部出てくる。

- y の .5 は下の行（x 主軸の線は上の角を含む＝下の行のひし形に触れる）、
  x の .5 は左の列（y 主軸の線は右の角を含む）。A4。
- 円の頂点が丸めでひし形の**辺**にちょうど乗ると、その画素はどちらの回り順でも点灯
  する（辺は外なので、そこで終わる線は「出た」扱い）。D4。
- 縦の線がひし形の上の角から上へ離れていくとき、その画素は点灯する（上の角を含む）。
  下の角から下へ離れていく場合は点灯しない。D7。
- 45° の線は x 主軸として扱う。y 主軸扱いだと D5 が 20 画素ずれる。

前回は「副軸方向へ無限小ずらす」規則で A〜C を説明していたが、D4（8画素）と
D7（1画素）が説明できなかった。ずらし方をどう選んでもこの2つと A4・A5 は
両立しない。角の所属を x/y 主軸で総当たり（16×16×2通り）すると、全ページで
誤差0になるのはこの表の組み合わせだけだった。

## 2. drawCircle — 半径で辺数が変わる多角形

**N = clamp(floor(r/2), 8, 16) 角形**。頂点は角度0（真右）から。

| r | 1–17 | 18–19 | 20–21 | 22 | 32 | 44 |
|---|---|---|---|---|---|---|
| N | 8 | 9 | 10 | 11 | 16 | 16 |

C1–C4（r=8..22 を1刻み）、C7（r=32）、C8（r=44）で、各円ごとに N と開始角を
総当たりし、全て誤差0で決まった。

- **未解決だった A1（r=22）は 11角形で誤差0。** 左右非対称なのは 11 が奇数だから。
- r=1..7 は八角形。r=3 が中点円と一致したのは偶然。
- r=2.4〜3.0 が全部描かれるのも、辺が1px未満でも線は描かれるから（1節）。
- 上限は **16**。D2 の r=34/38/42（floor(r/2) なら 17/19/21）が全部 16 角形だった。
- 小数半径は **floor**。D3 の r=17.5/17.9/19.5/19.9 が 8/8/9/9 角形（round なら 9/9/10/10）。
- 中心の小数部はそのまま効く。D1（C5 の撮り直し、中心 +0.25/+0.5/+0.75）が一致。
- 頂点の回り順は結果に効かない。D4 で一見効いているように見えたのは、1節の
  「辺は外」の規則のため（どちらの向きでも点灯する）。

## 3. 塗り — 画素の角で標本化

塗りは点標本で、**画素 (px, py) の標本点がスクリプト座標のどこにあるか**で決まる。

| 命令 | 標本点 | 縁ちょうどの扱い |
|---|---|---|
| drawCircleF | (px, py) — 左上角 | x を右へ、y を上へ無限小ずらす（F5 で訂正。9節） |
| drawTriangleF, drawRectF | (px, py+1) — **左下角** | x を右へ、y を上へ無限小ずらす |

drawCircleF だけ標本点が違う。A6 の3つの三角形（整数・+0.5・小数頂点）はこの規則で
全て誤差0、円塗りの規則だと 138 画素ずれる。逆に C9・A3 の塗り円は三角形の規則だと
328 画素ずれる。オフセットを 1/16 刻みで総当たりしても、両立する値は無かった。

- A6 の直角三角形 `(50,68),(70,68),(50,88)` が 19行（68..86）になるのはこのため。
  上端（y=68）はどちらの規則でも同じ行に来る。違いが出るのは下側の縁だけ。
- 面積0の三角形は何も描かない（D12）。巻き順は結果に効かない（D8）。
- 矩形を2つの三角形で描いたものと drawRectF は同じ画素になる（D8）。

## 4. drawRectF

三角形と同じ規則で、列は `ceil(x) .. ceil(x+w)−1`、**行は `floor(y) .. floor(y+h)−1`**
（B6・D7）。x と y で丸めの向きが逆になる。

| x, w | 20, 3 | 20.25, 3 | 20.5, 3 | 20.5, 3.5 | 20.75, 3 | 19.5, 3 | −0.5, 4 | 70, 0.4 | 60, 0 |
|---|---|---|---|---|---|---|---|---|---|
| 列 | 20–22 | 21–23 | 21–23 | 21–23 | 21–23 | 20–22 | 0–3 | 70 | なし |

y=20.25 は行 20 から、y=20.5 で高さ 6.5 なら行 20..26。幅 0.4 でも1列描かれる。
負の幅・高さは正の側に裏返したのと同じ画素（D7）。drawRect の負の大きさも同様。

## 5. drawRect — 4本の線のループ

`(x,y)→(x+w,y)→(x+w,y+h)→(x,y+h)→(x,y)` を線で引いたもの。B5 の8個全部が
画素単位で一致した。

- **大きさは (w+1)×(h+1)**。`drawRect(6,12,40,30)` は列 6..46・行 12..42。
- 閉じたループは同じ画素を2度踏まない。a=128 の枠でも角と辺は同じ明るさ（194）で、
  **角の二重ブレンドは無い**。
- 幅0 の枠も描かれる（同じ線を往復するので、半透明なら二重ブレンドの明るさになる）。
  B5 の幅0の枠は 1x1 の枠と重なる位置にあり、重なり回数どおり 1回 194・2回 206・
  3回 208 の明るさになっている。

## 6. 合成 — 4チャンネルブレンドと rgb×a 表示

B2・B3 は素直な src-over では説明できない（平均誤差 26、最大 121）。次のモデルで
Mac・Windows とも平均誤差 1.0（8bit 換算）で一致した。

```
dst.rgb ← α·src.rgb + (1−α)·dst.rgb
dst.a   ← α·α       + (1−α)·dst.a        ← アルファにも同じブレンド式
表示値   = dst.rgb × dst.a
```

`glBlendFunc(SRC_ALPHA, ONE_MINUS_SRC_ALPHA)` を4チャンネルに掛け、モニターが
フレームバッファを黒の上に合成して見せている形。

| 画面 | 実機 | このモデル | src-over |
|---|---|---|---|
| 黒地に白 a=128 を1回 | 96 | 96 | 128 |
| 同じく 2 / 3 / 5 回重ね | 119 / 126 / 126 | 120 / 126 / 128 | 192 / 224 / 248 |
| 灰(128)地に白 a=51 | 129 | 129 | 153 |
| 灰(128)地に白 a=204 | 193 | 193 | 230 |
| 白地に黒 a=17 | 221 | 223 | 238 |

値は B1 の不透明グレーランプを較正曲線にして、画面輝度から setColor 相当値へ
戻したもの。

- a=128 を何度重ねても **128 で頭打ち**になる（src-over なら 255 に近づく）。
- **フレームの最初の画素は (0,0,0,0)、アルファまで透明**（D9）。drawClear せずに
  白 a=128 を塗ると 32 相当（rgb=128、a=128²/255）で、不透明な黒の上の 96 とは違う。
  a=32 はほぼ見えない。10 秒待っても変化しないので、毎フレームこの状態に戻っている。
  Mac・Windows で同じ値。未描画の画素は不透明な黒よりわずかに暗く見える
  （画面輝度で 14 対 20）が、setColor 換算で 1 未満の差。
- a=0 は何も変えない。a=8 は変化が見える（下限は 1/255 刻み）。
- **drawClear はアルファを無視して置換**し、表示は rgb×a（B4：`setColor(0,255,0,128)`
  で全面が緑 128 相当）。前回「premultiply されている」と書いたのは、この表示側の
  掛け算を見ていた。
- B1 の伝達特性は Mac と Windows で数レベル違う（トーンマッピングの差）が、形は同じ。
  RGB 3色も同じ曲線。画面輝度はシーンのライティングを通った値なので、
  `setColor` の絶対値へ戻すには使えない。相対比較にだけ使っている。

## 7. 文字（B7）

- 4x5 グリフ、送り 5px、行送り 6px。小文字は大文字と同じ形。
- 小数座標は切り捨て（`drawText(0.5,…)` は x=0、`drawText(0,42.5,…)` は y=42）。
- 左端の見切れはそのまま描かれる（x=−3 の C は最後の1列だけ見える）。
- `drawTextBox` は語単位で折り返す。
- ASCII 32〜126 の全95文字を D10 で撮った。以前の `pixelFont.js` と形が違ったのは
  B7 で見つけた 18 字に加えて `\` と `` ` ``（`` ` `` はグリフ自体が無かった）。
  U・V・Z など手描きのままだった文字は実機と同じ形だった。小文字は全て大文字と同形。
- 文字座標の切り捨ては負の値でも同じ（`drawText(-0.5,…)` は x=−1 から）。D10。

### drawTextBox の折り返し規則（B7 から推定）

画素幅で語単位に折り返すと "WRAP THIS"（44px）は1行に収まるが、実機では収まらない。B7 の6行は次の規則で全部説明できる。

1. 1行の容量は `floor(w/5)` 文字（w=44 なら 8）。
2. 位置 pos から容量ぶん取り、直後の文字が空白でなければ、その中の最後の空白の
   直後で切る。空白は削らない。
3. 各行の幅は `文字数×5−1`（空白も数える）。中央揃えは `x + (w − 幅)/2` を切り捨て。

"wrap this box now please" は `"wrap "` / `"this box"` / `" now "` / `"please"`、
"centred text box" は `"centred "` / `"text box"` になる。行頭・行末の空白が
位置に効いているのが決め手で、各箱の1行目が単純な中央揃えより 2.5px 左に来るのは
末尾の空白のせい。D11 で、容量を超える単語は容量で切れる、`\n` で改行、連続空白も
そのまま数える、右揃え・下揃え、縦方向の高さは `行数×6−1`（`行数×6` ではない）、
w=45 と 49 で容量 9 文字、を確認した。

## 8. 画面の大きさと負の半径（E カード、2026-09-22）

`tools/ingame/verifyE_sizes.lua` を Windows（RTX 4070Ti）で撮影した。E1–E4 は
1x1・2x1・3x1・2x2・3x2・3x3・5x3・9x5 の8種類、E5–E7 は 3x3。

**画面の大きさ：規則は変わらない。** 32 枚全部が `raster.js` の予測と誤差0。

- 右端・下端の .5 の丸め、画面外への切り取り（E1）
- 30x21 の検証ブロックを画面全体に敷き詰めたもの（9x5 で54個）が全部同じ画素（E2）
- 画面幅いっぱいの緩い斜線（E3）
- 円の辺数（E4。r=3〜44）

`getWidth()`×`getHeight()` は1ブロック 32 画素どおり（E1 に表示した値）。

**負の半径：|r| の円と画素単位で同じ。** E5（輪郭 −22/−18/−19/−21）、E6（同じ
半径の塗り）、E7（同心の −44/−32/−26）が、|r| で描いたものと誤差0。

| 仮説 | E5 の誤差 | E7 の誤差 |
|---|---|---|
| 辺数 floor(r/2)（常に8角形。以前の PhySim） | 490 | 960 |
| 辺数 \|r\|、頂点は r で置く（奇数角形が左向き） | 324 | 120 |
| 辺数 \|floor(r/2)\|、頂点は \|r\| | 172 | 0 |
| **辺数も頂点も \|r\|** | **0** | **0** |

（誤差は撮影との点灯画素の差、missing＋extra。）
`raster.js` の `circleSides` / `circlePolygon` を |r| に直した。D12 の −10・−8 は
どちらの規則でも八角形なので、前回は分けられなかった。

### 解析側の変更

- `rectify.mjs` はモニターの大きさをファイル名（`E2_5x3.png`）から読む。目盛の
  本数、下端の目盛の位置、角で融合する目盛の除外を大きさから決める。
- 較正残差: 1x1〜5x3 は 0.009〜0.033px。9x5 は論理 1px が画面 5.3px しかなく
  0.058〜0.061px（worst 0.135px）だが、全ページ誤差0。`export-fixture.mjs` の
  上限を 0.05px から 0.1px にした（標本は画素の中央 0.25〜0.75 から取るので、
  0.25px 未満のずれでは隣の画素を読まない）。
- fixture のマスク（目盛の帯とページ番号）をやめた。緑の目盛と文字は輝度が最大
  137 で閾値 150 に届かず、帯の中の明るい画素は全部本物の白だった（B6・B7・D10・
  D12）。マスクを外しても A〜D の 27 ページは全部一致する。

## 9. 式で埋めていた範囲（F カード、2026-09-25）

`tools/ingame/verifyF_gaps.lua` の F1–F9 を 3x3 で、Mac（Apple M5）と Windows
（RTX 4070Ti）の両方で撮影した。較正残差は Mac 0.011〜0.016px、Windows
0.035〜0.040px（worst 0.098px）。

**図形：F1・F2・F4・F9 は PhySim の予測どおり誤差0。F5・F6 で塗り円の縁の扱いが
逆だったので直した。F3 は Mac と Windows で 17 画素食い違った。** F7・F8 の色は
`media/blend.js` の式どおりだった。

### 円の辺数の境目（F1・F2）

同心の輪郭 r=23, 25, 27, 29, 31, 33（F1）と r=24, 25.9, 28, 29.9, 31.9（F2）が
両プラットフォームとも誤差0。辺数は `floor(r/2)` で、r=23 から順に 11, 12, 13, 14,
15, 16、F2 は 12, 12, 14, 14, 15。round(r/2) なら F1 で 454 画素、F2 で 314 画素
違っていた。r=8〜44 の辺数がこれで全部撮影で決まった。

### 塗りの頂点の丸め（F3）

drawRectF の x・y、drawTriangleF、drawCircleF の頂点を 0 / 1/1000 / 1/512 / 1/300
ずらした表。

| 仮説 | Mac の誤差 | Windows の誤差 |
|---|---|---|
| 丸めない | 36 | 53 |
| 1/512 格子 | 36 | 53 |
| 1/128 格子 | 48 | 31 |
| 1/256 格子、タイは偶数へ | 20 | 3 |
| **1/256 格子、タイは上へ（PhySim の `Math.round`）** | **0** | 17 |

**塗りも線と同じく 1/256px に丸められる。** 1/1000 の列は丸めなしと、1/300 の列は
1/128 格子と、両プラットフォームで食い違う。F5・F6 の縁のテストはこの前提で読んだ。

**ちょうど 1/512（タイ）の列だけ、Mac と Windows で違う。** 食い違いは 17 画素で、
全部 x=55〜61 の3列目（drawRectF の x、drawTriangleF、drawCircleF）にある。1/1000・
1/300 の列、y をずらした行、下端の小数頂点の drawTriangle は一致した。

- Mac はどのタイも上へ丸める。PhySim の `Math.round` と画素単位で同じ。

## 10. 1/512px のタイ（G カード、2026-09-25）

`tools/ingame/verifyG_ties.lua` を撮影した。Windows（RTX 4070Ti）は G1・G2 を
1x1・2x1・3x1・2x2・3x2・3x3・5x3・9x5 の8種類、G3 を 3x3。Mac（Apple M5）は
G1〜G3 を 3x3。較正残差は 0.011〜0.063px、プローブの画素は点灯 170 以上・消灯 59 以下で、
閾値 150 との間は十分空いている。`tools/ingame/analysis/ties.mjs` で読んだ。

**20 ページのどこでも、同じ値のプローブは全部同じ向きになった。** drawRectF の左端・
右端、drawTriangleF の辺、drawCircleF の頂点、画面上の位置（G1 の a と d、G2 の a と d）
のどれも効かない。向きは、プラットフォーム・軸・モニターの大きさ・値だけで決まる。
Windows の x のタイは、同じ幅なら高さが違っても同じだった（3x1・3x2・3x3）。

### Windows（RTX 4070Ti）

| 軸 | 大きさ | 上へ丸めたタイ |
|---|---|---|
| x = k + 1/512 | 幅 32・64・288 | なし（全部下） |
| x = k + 1/512 | 幅 96 | k = 18, 21, 24, 26, 27, 29, 30, 32, 35, 38, 41, 44, 47, 48, 50, 51, 53, 54, 56, 57, 59, 60, 62, 63 |
| x = k + 1/512 | 幅 160 | 50 個（k = 16〜126 に散らばる） |
| y = k − 1/512 | 高さ 32・64・96・160 | 全部 |

偶数への丸めなら x は全部下、y は全部上になる。幅 32・64 は 2/W が2進でちょうど
表せる幅で、誤差が入らず偶数への丸めそのものになる。幅 96・160 では、x の一部だけが
上へずれる。**向きがモニターの幅で変わるのは、浮動小数の誤差で決まっている証拠。**

頂点の変換を 32bit 浮動小数で総当たりし（投影に半画素のずれをどこで入れるか、
乗算と加算を分けるか fma か、viewport の式、y の向き、タイの丸め方）、次の式が
x 946 個・y 472 個の全部に合った。

```
scale  = f(2/W)                                   f() は 32bit への丸め
ndc    = f( f(x · scale) + f(−1 + f(0.5 · scale)) ) 半画素のずれは投影の中
screen = f( f(ndc · f(W/2)) + f(W/2) )             viewport は乗算と加算を別々に
snap   = screen を 1/256 に偶数への丸め − 0.5
```

y も同じ式に H を入れて合う。次に合うのは viewport を fma にしたもので、95 個外れる。
fma を使わない乗算・加算と、偶数への丸め（D3D の固定小数点への変換規則）は、
Direct3D の頂点の流れとして自然な形。

`raster.js` の `snapUnits()` をこの式にした。線・塗りの全部の頂点が通る。
F3（17 画素）と G の 19 ページが全ページ画素単位で一致し、それまでの 68 ページも
変わらない。タイから離れた座標では、式の誤差（1e−5px 程度）は丸めに効かない。

### Mac（Apple M5）

- x のタイ（G1・G3、幅 96）は **全部上**。
- y のタイ（G2、高さ 96）は値によって分かれる。k = 11〜33 は全部下、34 から上と下が
  混ざり、上は 37 個（34, 37, 40, 43, 46, 49, 50, 52, 53, 55, 56, 58, 59, 61, 62, 64, 65,
  67, 68, 70, 71, 73〜80, 82, 83, 85, 86, 88, 89, 91, 92）。F3 の 34−1/512 が上だったのは
  たまたまだった。
- 上と同じ総当たり（2,304 通り）で、y に合う式は見つからなかった（最良で 83 個中 12 個
  外れる）。Mac は別の頂点の流れ（Metal への変換層を含む）を通っていると考えられる。

PhySim は Windows に合わせたので、Mac でちょうど 1/512 のタイに頂点を置くと、1画素
ずれることがある（G1 で 930 画素、G2 で 638 画素、G3 で 66 画素、F3 で 17 画素）。
それ以外の Mac の撮影は全部 PhySim と一致する。

### fixture

F3 と G のページ（tie pages）は、Mac と Windows が食い違っても止めず、Windows の撮影を
使い、Mac との差を表示する（`export-fixture.mjs`）。ほかのページはこれまでどおり
1画素でも違えば止まる。fixture は 86 ページになった。

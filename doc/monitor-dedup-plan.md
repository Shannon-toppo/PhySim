# モニター描画の重複除去をスタンプバッファ化する計画

作成日: 2026-08-25
対象: `media/mcScreen.js` の `plotter()`
前提: v0.4.5 の ImageData バッファ化（`doc/worklog.md`「モニター描画の CPU 使用率調査と修正」）が入っていること

| フェーズ | 内容 | 状態 |
|---|---|---|
| 1 | 不透明色のときは重複除去自体をやめる | v0.4.5 で実装済み |
| 2 | 半透明パスの `Set` をスタンプバッファに置換 | 未着手 |

---

## 背景

`plotter()` は raster.js のラスタライザに渡すピクセル書き込みコールバックで、図形ごとに
`Set` を作って同じピクセルへの二度書きを弾いている。円の 8 方向対称が軸上で合流する点や、
三角形の角のように、ラスタライザが同じピクセルを 2 回訪れる箇所があるため。

除去が要るのは**半透明色を二重合成して明るい点を作らないため**であって、
不透明色なら 2 回書いても結果は同じ（冪等）。この観察が計画全体の前提になっている。

## 実測

プロトタイプを 2 種類つくり、同一ページに新旧モジュールを並べて読み込んで A/B した
（96×96 モニター 1 枚、1 フレームあたりの再描画時間）。

| ワークロード | 現状（Set） | 不透明のみ除去スキップ | + スタンプバッファ |
|---|---|---|---|
| 混在 500 cmd 不透明 | 0.570 ms | 0.338 ms | 0.328 ms |
| 混在 2000 cmd 不透明 | 2.014 ms | 1.316 ms | 1.318 ms |
| 混在 500 cmd α=128 | 1.032 ms | 1.052 ms | 0.838 ms |
| 枠線のみ 500 cmd 不透明 | 0.658 ms | 0.186 ms | 0.186 ms |
| 枠線のみ 500 cmd α=128 | 0.842 ms | 0.850 ms | 0.368 ms |

読み取れること:

- 不透明コンテンツでは、**スキップだけで利得の全部が取れる**（スタンプ版との差は誤差）。1.7〜3.5 倍
- スタンプバッファが効くのは**半透明の線・円・三角形の枠を描く場合だけ**。そこでは 1.2〜2.3 倍

出力の一致は不透明 / α=128 / 枠線 α=64 / 枠線不透明の 4 種で新旧キャンバスの
`getImageData` を全ピクセル比較し、差分 0 を確認した。

## フェーズ 1（実装済み）

`plotter()` を色に応じて 2 つのクロージャに分けるだけ。新しい状態もメモリも増えない。

```js
if (col.a === 255) {
  const packed = col.packed;
  return (x, y) => {
    if (x < 0 || y < 0 || x >= width || y >= height) return;
    u32[y * width + x] = packed;
  };
}
// 半透明のときだけ Set（フェーズ 2 でスタンプに置換）
```

図形ごとの `Set` 確保も不透明パスでは消える。

## フェーズ 2（未着手）

### データ構造

- `Monitor` に `stamp: Uint32Array | null` を追加。**遅延確保**（半透明の枠を初めて描いたときだけ）。
  半透明枠を描かない MC ではメモリ 0
- サイズは `width * height` 語。96×96 で 36 KB、Stormworks 最大の 9×9 ブロック（288×288）で 331 KB
- 世代カウンタはモジュール横断で単調増加。図形ごとに 1 つ ID を取り、`stamp[i] === id` なら描画済み

### ID ライフサイクル

この計画で唯一ロジックらしいロジックがここ。

- ID は **1 から**開始する。新しく確保したバッファはゼロ埋めなので、0 を ID にしなければ
  「未使用」と衝突しない。モニターをリサイズで作り直しても同じ理由で安全
- カウンタが `0xffffffff` に達したら、生きている全モニターのスタンプをゼロ埋めして 1 から再開。
  60 fps × 半透明枠 1000 個/フレームでも約 20 時間に 1 回で実質通らないが、
  通ったときに壊れないことは保証が要る

この部分だけを純粋モジュールに切り出す（1 図形につき 1 回しか呼ばれないので呼び出しコストは無視できる）。

```js
// media/stamp.js
export const STAMP_MAX = 0xffffffff;
export function createStampCounter() { return { seq: 0 }; }
export function nextStampId(counter, buffers) { /* 0 を返さない / 上限でリセット */ }
```

ピクセル単位の判定（`if (stamp[i] === id) return;`）は `mcScreen.js` にインラインのまま残す。
ここを関数呼び出しにすると最適化の意味が薄れる。

### テスト

`test/stamp.test.mjs` を新規追加:

- `nextStampId` は 0 を返さない（ゼロ埋めバッファとの衝突を防ぐ不変条件）
- 連番で増える / 異なる図形が同じ ID を共有しない
- `STAMP_MAX` に達したら渡されたバッファを全部ゼロ埋めして 1 から再開する
- リセット直後の ID が、リセット前に書かれた値と衝突しない

`media/mcScreen.js` は Node から import できない（`dom.js` が `getElementById` する）ので、
描画結果の担保は下の手動検証で行う。

## 検証手順（フェーズ 1・2 共通）

1. `git show HEAD:media/mcScreen.js > media/_oldMcScreen.js` で旧版を並べて置く
2. `panel.html` の `{{...}}` を埋めたプレビューページを立てる（`media/` を静的配信し、
   CSP メタタグを外し、`acquireVsCodeApi` をスタブする。importmap の値は `./` 始まりにすること
   —— ベア指定子は import map に書けず、値が null 扱いになって解決に失敗する）
3. 両モジュールを `import()`（モジュールキャッシュを避けるためクエリ文字列を付ける）し、
   同じ `screenConfig` を渡す
4. 同一のコマンド列を両方に描かせ、2 枚のキャンバスの `getImageData` を全ピクセル比較。
   **不透明 / α=128 / 枠線 α=64 / 枠線不透明の 4 種で差分 0** を確認
5. `npm test` / `npm run lint` / `npm run check:media`
6. プロトタイプ用ファイル（`media/_oldMcScreen.js`、プレビュー HTML）を削除

> ベンチマーク時の注意: v0.4.5 で再描画を rAF に載せたため、ページが非表示だと
> `repaintPending` が立ったまま再描画が止まる（意図どおりの挙動）。同期的に測りたい場合は
> `repaint()` を呼ぶ一時的な export を足すこと。

## 却下した案

- **Uint8Array のスタンプ**（255 図形ごとにゼロ埋め）: メモリは 1/4 だが、288×288 で 83 KB の
  ゼロ埋めが 1 フレームに数回走る。節約分が消える
- **図形ごとにバウンディングボックスだけクリア**: 管理コストが除去コストを上回る
- **`Set` を 1 個使い回して `clear()`**: `has`/`add` が 1 ピクセル 21 ns かかる本体は変わらない
- **半透明でも除去をやめる**: 円の 8 方向対称の合流点や三角形の角が二重合成されて明るい点になる。
  除去の存在理由そのもの

## フェーズ 2 を今やらない理由

ImageData 化で 500 cmd/tick の再描画は既に 0.45 ms（16.7 ms 予算の 3%）まで下がっており、
フェーズ 1 でさらに 0.33 ms になる。フェーズ 2 の削減幅は**半透明の枠線を多用する MC でしか
現れない**ので、実際にそういうスクリプトで重いという報告が出てから着手すればよい。
